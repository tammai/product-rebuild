# Contracts 1.1.1: CLI output never crashes on a non-UTF-8 console

## Why

`contracts.py`'s CLI prints non-ASCII text (`routed: X → rspec`, and `…` / `→` / `—` in many messages). On a Windows console whose encoding is cp1252, `print` raises `UnicodeEncodeError` and the command crashes with a traceback instead of its result and exit code. Found by sdlc part 3 and bug-hunter part 1.

**Request (verbatim, via the Orca coordinator, task W1c):** "Contracts 1.1.1, a patch (user approved): contracts.py's CLI crashes printing a non-ASCII arrow (e.g. 'routed: X → rspec') on a Windows console whose encoding is cp1252 (found by sdlc part 3 and bug-hunter part 1). Fix it so output never crashes on a non-UTF-8 console (e.g. reconfigure stdout with errors='replace' or print ASCII '->'; keep messages otherwise unchanged), with a failing test first that runs the CLI with PYTHONIOENCODING=cp1252. Also re-copy 01-shared-contracts.md from C:/Users/Admin/orca/rebuild-upgrade (C4 now notes the cli format is not settled in v1, a known limit; no code change for that)."

Spec: [docs/specs/rebuild-upgrade/01-shared-contracts.md](../../specs/rebuild-upgrade/01-shared-contracts.md) (C4 note re-copied; no code change).

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `main()` reconfigures stdout and stderr with `errors="replace"`; a character the console can't encode prints as `?` | printing ASCII `->` | `→`, `…` and `—` appear in dozens of messages and in user data (paths, IDs); replacing one arrow would leave the rest crashing. Messages stay byte-identical on a UTF-8 console |
| Streams without `reconfigure` (a test's `StringIO`, an embedding caller's wrapper) are left alone | wrapping them | they already accept any `str` |
| Contracts version 1.1.1 (patch) | 1.2.0 | no format or rule changes; only console output |

- **AC-002** Given `contracts/v1/` at 1.1.1, when `contracts.py vendor-check` runs, then every file carries the `contracts-version: 1.1.1` header and MANIFEST matches. `[request]`
