# Contracts 1.3.0: the lock check rejects an [inferred] criterion at level 1

## Why

**Request (verbatim):** "- product-rebuild todo: make contracts.py lock reject an [inferred] criterion at level 1. That would be contracts 1.3.0, and every repo would need to copy it again. […] do 2 items, drop 2 other".

Contracts 1.2.0 says an `[inferred]` criterion never reaches level 1 by audit, but only in words: `check_lock` accepts such a lock. This makes C3's rule mechanical, closing the todo filed by 2026-11-11-s-contracts-1-2-0.

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `error` for `tag: inferred` with `level: 1`; level 2 stays allowed | Also rejecting level 2 | C3 1.2.0 keeps level 2 for a recorded test that passed against the reference, which is evidence in its own right |
| 1.3.0 (minor) | 1.2.1 | A new error a lock can hit; the user's earlier call put rule changes at minor. Only rspec runs `check_lock` (on the lock it writes), and rspec stops producing such a lock when it re-vendors |
| A new invalid fixture `fixtures/lock/invalid/inferred-at-level-1.json` | A unit test only | `vendor-check` runs every fixture, so each consumer's drift test proves the rule too |

## Acceptance criteria

- **AC-001** Given a lock with a criterion tagged `inferred` at level 1, when `check_lock` runs, then it reports an error naming the criterion; at level 0 or level 2 (with a test) it reports none for that rule; and the new invalid fixture fails `vendor-check`'s verdict as expected.
- **AC-002** Given `contracts/v1/` at 1.3.0, then `VERSION` is 1.3.0, every header says 1.3.0, and MANIFEST matches.
