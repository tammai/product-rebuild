# Contracts 1.3.1: the departures check accepts equiv-trace:<name>

## Why

**Request (verbatim):** "Fix GitHub issue #36: contracts.py check_departures refuses match rule equiv-trace:<name>, which product-rebuild's equiv.py accept writes; accept it (non-empty name) in the departures check and make the oracle treat it as never matching an HTTP value." (tammai/bug-hunter#36)

**Proof:** a `departures.yaml` entry with `match: [{runner: http, rule: "equiv-trace:invoices-total"}]` (what `equiv.py accept` writes) fails `check_departures` with `D-004 match 1: unknown rule equiv-trace:invoices-total (uuid, int, iso8601, same-as:<capture>, regex:<pattern>)`, so bug-hunter's `/hunt --oracle` stops on any workbench with an accepted trace.

**Root cause:** `check_departures` checks each match rule with `_rule_problem`, the HTTP replay step vocabulary, which has no `equiv-trace:`.

## Decisions

- Accept `equiv-trace:<name>` (name non-empty) in `check_departures` only; HTTP replay steps keep their vocabulary, so the rule can't appear in a recorded test. Ruled out: adding it to `_rule_problem`, which steps share.
- No change to `_rule_ok`: it already returns False for the rule, so the oracle never matches a replayed value with it.
- 1.3.1 (patch): it accepts a registry 1.3.0 wrongly refused and adds no error. Settled-in-v1 table names the rule.

## Acceptance criteria

- **AC-001** Given a departure whose match rule is `equiv-trace:invoices-total`, when `check_departures` runs, then it reports no issue, and `_rule_ok` never accepts a value for that rule; `equiv-trace:` with an empty name is still refused.
- **AC-002** Given `contracts/v1/` at 1.3.1, then `VERSION` is 1.3.1, every header says 1.3.1, and MANIFEST matches.
